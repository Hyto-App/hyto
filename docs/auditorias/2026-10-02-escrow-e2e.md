## Hypothesis

**Friendbot / account creation is missing from `/api/usdc` when the account is not on testnet. Confirmed.**

`POST /api/usdc` with `accion: "preparar"` loads `https://horizon-testnet.stellar.org/accounts/{session wallet}`. A Horizon 404 returns 400, `AVISO_USDC_SIN_CUENTA` ("This account isn't on the test network yet. Sign in again and retry."). Nothing in that handler calls Friendbot, `requestAirdrop`, `createAccount`, or Cavos `addTrustline`. The unit test `sin cuenta en testnet no se arma la trustline` locks this (`lib/api/usdc.test.ts`). Signing in again does not create the account.

Two different creation tools exist elsewhere, and neither is this button:

| Tool | Where | What it does |
|---|---|---|
| Friendbot | `scripts/hito-prueba.ts` only (`https://friendbot.stellar.org?addr=`) | Creates a classic testnet account and funds it with XLM. Stellar documents this as the testnet way to create an account. There is no Friendbot on mainnet. |
| Cavos sponsored deploy + `addTrustline` | `asegurarCobroUsdc` in `lib/integrante/usdc.ts`, called from `prepararIdentidad` / the old `/cuentas/preparar` demo screen | If `wallet.status === "undeployed"`, calls `billetera.execute`, then `addTrustline`. The comment there says a sponsored account is born with 0 XLM. |

**Get ready to be paid** (`components/sesion/PrepararUsdc.tsx`) calls `prepararUsdcDeSesion` → `/api/usdc`, not `asegurarCobroUsdc`. So a Cavos address that Horizon does not know yet cannot open a USDC trustline from the Account screen. A classic account that does exist still needs XLM for the fee and the trustline reserve, because this path builds a self-paid `changeTrust` (`lib/integrante/trustline.ts`). Fee-bumps are rejected on the escrow path and on this trustline path.

Friendbot is the right manual step for a classic `G…` that is missing or has no XLM. It is the wrong assumption for a still-undeployed Cavos smart account: the kit path deploys it sponsored, and Friendbot would instead create a classic account at that address. This audit does not claim which of those two a given Cavos login returns. The code treats both the same: Horizon 404, then stop.

The same hole exists for the organizer. `rechazoSiFondos` (`lib/escrow/saldo.ts`) returns "This wallet is not on the network yet." on Horizon 404, and never asks Friendbot. It also checks USDC only, not XLM. An organizer who has USDC and no XLM passes the preflight and fails later, because v2 rejects fee-bumps and the Cavos account must pay the fee (`lib/escrow/modulo.ts`, `lib/api/firma.ts`).

## Flow map

One Trustless Work v2 multi-release contract per task, on Stellar testnet. Base `https://beta.api.trustlesswork.com` (`lib/escrow/cuerpos.ts`). The API never signs. Hyto builds, the Cavos wallet signs `unsignedXdr` as returned, then the server submits `POST /stellar/send-transaction`. Testnet USDC issuer `GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5`. The SAC id is derived in `lib/escrow/desplegar.ts` (`USDC_SAC_TESTNET`). Platform fee is 0. The organizer is approver, service provider, and release signer. The volunteer is only the milestone receiver.

```
Cavos login
  POST /api/sesion          JWT checked, cookie hyto_sesion, wallet from JWT if present
  POST /api/sesion/wallet   stores the Cavos G… for this session
        |
        v
Account — Get ready to be paid
  GET  /api/usdc            Horizon account; { listo: true } only if the USDC trustline exists
  POST /api/usdc preparar   unsigned changeTrust for the session wallet (testnet)
  Cavos signXdr
  POST /api/usdc enviar     Horizon POST /transactions, after the server checks the XDR
        |
        v
Evidence upload (assigned member)
  POST /api/evidencias      wallet_cobro := session wallet (G… only)
        |
        v
Review — Lock budget          POST /api/firma accion=desplegar, then fondear
  preflight: organizer of the event, USDC balance >= amount + 1,
             receiver on testnet with the USDC trustline,
             HYTO_ESCROW_ADMIN / PLATFORM / RESOLVER distinct,
             reimbursement monto_confirmado inside the cap
  HMAC token (10 min) binds user, session, XDR hash, action, task, amount

        |

  marcar  → POST /escrow/multi-release/v2/change-milestone-status   (organizer as serviceProvider)

  liberar → POST /escrow/multi-release/v2/release-funds             (milestone index 0)
```

Demo (`demo-organizador@hyto.demo`, `demo-voluntario@hyto.demo`) is rejected before prepare and submit (`lib/sesion/demo.ts`, both firma routes) and before `/api/usdc`. The Account button is not rendered in demo.

## What works on main

These are enforced in code and covered by unit tests. They are not a substitute for a live payment.

1. **Session wallet.** Email/OTP and Google login connect Cavos on testnet (`appSalt` `hyto`) and store `billetera.address` via `POST /api/sesion/wallet` (`lib/auth/cliente.ts`). A second, different `G…` in the same session is rejected. If the Cavos JWT has no account, the first client-supplied `G…` is stored. The comment in `lib/api/sesion.ts` says that does not prove key control. Submit does not trust that string as the signer: the signer is read from the XDR and must equal `sesiones.wallet` (`lib/escrow/xdr.ts`, `lib/api/firma.ts`).
2. **Demo cannot sign or open USDC.** 403 on `/api/firma`, `/api/firma/enviar`, and `/api/usdc`. Horizon is not called for a demo USDC prepare.
3. **Trustline XDR is narrow.** One testnet `changeTrust` for that exact USDC code and issuer, source equal to the session wallet, limit greater than zero, ed25519 signature checked, fee-bump rejected (`lib/integrante/trustline.ts`). A body field `wallet` is ignored; the session wallet is the source.
4. **`wallet_cobro` comes from the assigned member's session**, not from a free-form field, on upload (`lib/api/evidencias.ts`). Deploy can backfill it from `walletDeUsuario` when evidence exists and the task field is empty (`lib/api/firma.ts`).
5. **Receiver preflight before deploy (#100).** `estadoReceptorUsdc` requires the payout account on Horizon testnet and a USDC balance line for this issuer. A balance of 0 still counts as ready. Horizon 5xx/timeout is 503, not the "not ready" message (`lib/escrow/receptor.ts`). This closes C1 from the September audit. `docs/AUDIT-2026-09-30.md` (status table written against `2b9fad4`), `AGENTS.md`, and `STACK.md` still say the check does not exist. That is doc drift. The check does not run again on fund-only.
6. **Organizer USDC preflight.** Deploy, fund, and submit require balance ≥ amount + 1 USDC (`RESERVA_USDC` in `lib/escrow/saldo.ts`). Horizon 404 is a 400. A read failure is 503.
7. **Role accounts.** `HYTO_ESCROW_PLATFORM`, `HYTO_ESCROW_RESOLVER`, and `HYTO_ESCROW_ADMIN` must be present, valid `G…` addresses, distinct from each other, and distinct from the organizer and the receiver (`lib/escrow/desplegar.ts`). Missing or colliding values fail before Trustless is called. They are not looked up on Horizon. Happy-path deploy/fund/pay does not need them to hold USDC (fee is 0 and they do not sign those steps). They must exist on testnet before anyone can sign a dispute as resolver.
8. **Reimbursement amount (#69).** Deploy and fund use `monto_confirmado`, capped by the task. A client-supplied fund amount is replaced for a reimbursement. A work task still sends the client's `monto` (see ranked fixes).
9. **HMAC prepare token.** `HYTO_TOKEN_SECRET` of at least 32 characters. In production, prepare and submit return 503 without it (`lib/api/preparado.ts`). The token is HMAC-SHA256 over user, session, XDR hash, action, task id, amount, and expiry (10 minutes). Submit rejects a missing token, a bad mac, a mismatch, or an expiry. The token does not include `contractId`.
10. **Fund resume (#67).** If a contract is stored and the indexed balance is exactly false (zero), the review screen shows **Finish locking** instead of **Lock budget** (`lib/admin/remoto.ts`, `components/admin/Revision.tsx`). A failed fund in the same click sets that state before the detail reload.
11. **Pay is gated on a positive indexed balance.** **Approve and pay** needs `en revisión`, a contract, and `fondeado === true`. A grade does not pay. The three calls are separate: mark, approve, release. A failed step resumes from that step (`pasosDesde`).
12. **Paid is strict.** `hash_pago` and `pagado` are written only for `release_funds` on this task's contract, a confirmed v2 submit (`STELLAR_TX_SUBMITTED`, `STELLAR_TX_SUBMITTED_INDEXER_LAGGING`, or a returned `contractId`), a 64-hex hash, and a re-read whose milestone 0 has `released` or `flags.released` (`lib/api/firma.ts`). **View payment** is the stellar.expert testnet link (`lib/escrow/cuerpos.ts` `enlacePago`).

## Blockers to a real testnet payment

Ordered by how they stop a human who already has two Cavos testnet wallets.

### 1. The payout account is never created by the app

If Horizon returns 404, **Get ready to be paid** stops. The copy says to sign in again. The organizer then sees the same 409 as a missing trustline: "Ask them to open the task and tap Get ready to be paid." (`lib/escrow/receptor.ts` uses one code for "account missing" and "no USDC line"). Trustless still rejects deploy with `ESCROW_RECEIVER_TRUSTLINE_MISSING` if that preflight is skipped. The organizer has the same creation gap, plus an unchecked XLM balance for fees.

### 2. A lagging deploy is not saved, so Lock budget can run twice

Trustless returns the future `contractId` on build. `STELLAR_TX_SUBMITTED_INDEXER_LAGGING` means the transaction was submitted and the read model has not caught up. The docs say to poll `GET /escrows/{contractId}`, not to deploy again.

Hyto treats that code as a successful submit (`envioConfirmado` in `lib/escrow/modulo.ts`) and then **refuses to store the contract** (`contratoDeServidor` in `lib/api/firma.ts`). The predicted id sits in the process-local `Map` `contratosPreparados`, and that branch does not read the map. The map is also empty on another Vercel instance. The HMAC token does not carry the id. The client may still hold the id from the prepare response and continue to fund in the same click, while `tareas.contrato_escrow` stays null. After a refresh, **Lock budget** is offered again. A second deploy creates a second escrow. The unit test `el indexador atrasado no guarda el contrato de memoria` locks the current (unsafe) behavior.

This is still C2 from the September audit.

### 3. A lagging release does not record `hash_pago`

Submit can be confirmed while `GET` still shows the milestone as not released. `guardarResultado` then returns 200 with an aviso and does not set `pagado` or `hash_pago`. **View payment** stays hidden. Retrying release can fail once the chain has already released, and nothing later writes the hash. That matches "no closed payment hash in the repo" even after a successful on-chain release.

### 4. Unknown indexed balance hides both buttons

`fondear` is shown only when `fondeado === false`. `pagar` only when `fondeado === true`. `leerFondeo` returns null on a non-OK read or a balance that is not a positive/zero number, and the screen ignores null (`components/admin/Revision.tsx`). After a reload, a contract with an unreadable balance shows neither **Finish locking** nor **Approve and pay**. The same-session fund path forces `fondeado` true only until reload.

### 5. Operational, not code: USDC and XLM are not fauceted

The app does not mint testnet USDC and does not call Friendbot for the organizer. A real payment needs, outside Hyto:

- Organizer: the account on testnet, enough XLM for Soroban fees, and USDC ≥ milestone + 1.
- Volunteer: the account on testnet, enough XLM to pay the `changeTrust` fee and reserve, and the USDC trustline (balance may be 0).
- Server: `TRUSTLESS_API_KEY`, `HYTO_TOKEN_SECRET` (≥ 32 chars), and three distinct role accounts in `HYTO_ESCROW_ADMIN`, `HYTO_ESCROW_PLATFORM`, `HYTO_ESCROW_RESOLVER`.

`HYTO_STELLAR_NETWORK=public` (or `mainnet`) points only the USDC balance read at public Horizon. The escrow API stays on the testnet beta host. Setting that variable makes the preflight look at mainnet balances.

## Failure modes

| Case | What the code does |
|---|---|
| Missing USDC trustline on the receiver | Deploy prepare returns 409 `receptor_no_listo` before Trustless. Same aviso as a missing account. |
| Receiver or organizer not on testnet | Receiver: 409, same as a missing trustline. Organizer balance: 400 "not on the network yet." `/api/usdc` prepare: 400, no Friendbot. `GET /api/usdc` on 404 returns `{ listo: false }`, so the button still shows. |
| `INDEXER_LAGGING` on deploy | Submit is 200. `contrato_escrow` is not saved. Client may still see the predicted id for the rest of that click. |
| Deploy ok, fund fails | If the contract was saved, **Finish locking** calls `fondear` only. Receiver trustline is not re-checked. If the contract was not saved (lagging), the screen goes back to **Lock budget**. |
| Indexed balance unreadable | Neither finish-lock nor pay. |
| Demo | 403 on firma prepare, firma submit, and USDC. Account button hidden. |
| HMAC missing, expired, or for another XDR | 409. Production without `HYTO_TOKEN_SECRET`: 503. |
| Fee-bump | 400. The signer must pay XLM. |
| `HYTO_ESCROW_*` missing, not a `G…`, or repeated | 503 for missing, 400 if a role collides with the organizer or the receiver. No on-chain existence check. |
| Release submitted, milestone not yet `released` in the read model | 200, task stays unpaid, no `hash_pago`. |
| Work-task fund amount tampered in the body | Sent to Trustless as given, after the organizer USDC check. Reimbursements are overwritten server-side. |

## Reproduction checklist

For two people with real Cavos testnet wallets. Do not paste seeds, API keys, or JWTs into tickets or this repo. Demo login cannot complete this list.

1. Confirm server env names exist and are non-empty: `TRUSTLESS_API_KEY`, `HYTO_TOKEN_SECRET` (32+ characters), `HYTO_ESCROW_ADMIN`, `HYTO_ESCROW_PLATFORM`, `HYTO_ESCROW_RESOLVER`, `DATABASE_URL`, `NEXT_PUBLIC_CAVOS_APP_ID`. The three role accounts must be different `G…` addresses, and different from both humans. Leave `HYTO_STELLAR_NETWORK` unset so balance reads stay on testnet. Leave `HYTO_DEMO_LOGIN` unset.
2. Both humans sign in with email or Google, not demo. On Account, confirm the shown `G…` is the Cavos address.
3. For each `G…`, open Horizon testnet `GET /accounts/{G…}`. If it is 404, the in-app button will not create it. Fund that classic account with Friendbot (`https://friendbot.stellar.org?addr=` plus the public address only), or deploy it with Cavos if the wallet is still undeployed. Wait until Horizon returns the account. Repeat for the organizer: they need XLM for fees, not only USDC.
4. Volunteer: Account → **Get ready to be paid** → confirm the Cavos prompt. Success is a stellar.expert testnet link, or the screen already saying the account is ready. Horizon must show a USDC balance line for issuer `GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5`. Balance 0 is enough.
5. Organizer: obtain testnet USDC (not from this app) greater than the milestone plus 1 USDC.
6. Organizer creates an event and assigns the volunteer. Volunteer opens the task and uploads evidence with the camera (work) or a PDF/JPEG/PNG/WebP (receipt). The task's payout account must become the volunteer's `G…`.
7. For a reimbursement, organizer confirms an amount within the cap before locking.
8. Organizer, review screen: **Lock budget**. Confirm twice (deploy, then fund). If the second confirmation fails and the budget reference is visible under Technical details, use **Finish locking** only. Do not start a second lock if a `C…` already exists on the task or in that panel.
9. After the indexed balance is above zero, **Approve and pay**. Confirm mark, approve, and release. If a step fails, use the same button; it resumes at that step.
10. The task should read paid, and **View payment** should open `https://stellar.expert/explorer/testnet/tx/` plus a 64-hex hash. Copy the hash into the team record. Do not commit it with a secret. If the chain shows the release and Hyto does not, the indexer-lag gap above is what happened: keep the hash from the wallet or from stellar.expert and do not release again.
11. Negative checks, if you have time: demo still 403 on pay; a volunteer who never tapped **Get ready to be paid** blocks **Lock budget** with the payout message; an organizer without the USDC reserve is blocked before Trustless; swapping `HYTO_ESCROW_*` so two roles match is blocked before Trustless.

## What this PR does not change

Behavior is unchanged. Two comments mark the 404 path and the indexer-lag path so the next change does not treat either as "nothing happened." No migration, no new `NEXT_PUBLIC_` variable, no secret.
