# Hyto full app audit — 2026-10-02

Findings only. This document does not change app behavior.

- **Repo:** [Hyto-App/hyto](https://github.com/Hyto-App/hyto), `main` at `53ec93c` (`La bandeja y la revisión se actualizan solas`, #99).
- **Network:** Stellar **testnet** only. No mainnet transaction was built, signed, or submitted. No secret, `.env` value, or private key is in this file.
- **Method:** read of the current tree (auth, account/trustline, volunteer flows, organizer escrow, demo, UI copy, leftovers from [docs/AUDIT-2026-09-30.md](../AUDIT-2026-09-30.md)). The status table at the top of that older audit was written against `2b9fad4` and is stale relative to #93, #94, #98, #100, and #101.
- **Stellar context:** the Stellar Raven MCP was not signed in for this run. Protocol facts below come from public Stellar docs, not from a Raven tool call: [Create an account](https://developers.stellar.org/docs/build/guides/transactions/create-account) (Friendbot funds a **testnet** account; there is no Friendbot on mainnet) and Circle's testnet USDC trustline quickstart (`changeTrust` for issuer `GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5`). A classic trustline cannot be submitted until the account exists and can pay the fee plus the trustline reserve. Hyto's issuer constant matches that testnet issuer (`lib/integrante/identidades.ts`).

A new Gmail volunteer is auto-inserted as `voluntario` (`lib/api/sesion.ts`). Organizer is never assigned on that path. The payment path still has **no closed testnet USDC hash in the repo**: the seed writes `hashPago: null` (`lib/db/semilla.ts`).

Parallel write-ups already open, and not merged here: escrow path audit #104, UI audit #89, Google return #18. This report is the full-app list. Follow-up agents should implement once, not three times.

## 3. Findings

### F1 — P0 — New Cavos wallet is not a testnet account

**Where:** Account → **Get ready to be paid** (`/cuentas`). `lib/api/usdc.ts`, `lib/integrante/trustline.ts`, `lib/integrante/usdc.ts`, `components/sesion/PrepararUsdc.tsx`, `components/admin/Entrar.tsx`.

**How to reproduce**

1. Sign in with Google or email as a person who has never been funded on testnet. Cavos returns a `G…`. The sign-in card says "Your Stellar wallet is created for you" (`components/admin/Entrar.tsx`).
2. Open **Account**. `GET /api/usdc` treats Horizon 404 and "no USDC line" the same (`listo: false`), so the button appears.
3. Tap **Get ready to be paid**. `POST` `accion: "preparar"` loads `https://horizon-testnet.stellar.org/accounts/{G…}`. Status 404 returns `AVISO_USDC_SIN_CUENTA`: "This account isn't on the test network yet. Sign in again and retry."
4. Signing in again does not create the account. Friendbot is only in `scripts/hito-prueba.ts` and in an error-text regex (`lib/ui/claro.ts`). The product path never calls it.
5. The sponsored path does exist: `asegurarCobroUsdc` calls `wallet.addTrustline` after an `undeployed` `execute` (`lib/integrante/usdc.ts`). It is wired from the legacy demo OTP helper (`lib/integrante/preparar.ts`, `/cuentas/preparar`), not from `PrepararUsdc`.
6. The XDR that **is** built is a self-paid classic `changeTrust` (`lib/integrante/trustline.ts`). That needs an existing account and enough testnet XLM for the fee and the trustline reserve. Manual Friendbot fixes one address only, which matches Raúl.

**Impact**

- **New Gmail volunteer:** cannot become payable. The panel can already say "This wallet is not on the test network yet" (`components/integrante/PanelCuenta.tsx`) and still offer a button that fails.
- **Organizer:** #100 blocks **Lock budget** with "Ask them to open the task in Hyto and tap Get ready to be paid" (`lib/escrow/receptorAvisos.ts`). The button is on **Account**, not on the task page (`app/(integrante)/tareas/[id]/page.tsx` renders only `SubirEvidencia`). Horizon 404 and a missing trustline share one organizer message.
- `firmarConCavos` does not check `wallet.status === "ready"` before `signXdr` (`lib/escrow/firmarCliente.ts`). `needs-device-approval` is handled only on the unused sponsored path.

**Suggested fix (do not implement here)**

Testnet only. Before any `changeTrust`: if Horizon returns 404, create the account (Friendbot, or the Cavos deploy the sponsored helper already attempts). Then add the USDC trustline with `wallet.addTrustline` when the wallet is not `ready` only after device approval. Keep `/api/usdc` as a read of `{ cuentaExiste, trustline }`. Point the organizer copy at **Account**. A parallel onboarding agent must still retire the self-paid prepare path; funding XLM alone leaves the button on the wrong implementation.

### F2 — P0 — Escrow id is not durable across instances

**Where:** `lib/api/firma.ts` (`contratosPreparados` map, `contratoDeServidor`).

**How to reproduce**

1. Organizer with testnet XLM, testnet USDC, and a volunteer who already has a trustline: **Lock budget** (deploy, then fund).
2. Prepare stores the predicted `C…` only in the process map.
3. Submit hits another Vercel instance, or the process restarted, and Trustless returns `STELLAR_TX_SUBMITTED_INDEXER_LAGGING` without `contractId`.
4. `contratoDeServidor` returns an aviso and does **not** write `tareas.contrato_escrow`. The same gap applies to a release that cannot be re-read: `hash_pago` stays empty (`guardarResultado`).
5. The task can be deployed again because the row still has no contract. Two overlapping submits before either write can both land; the DB keeps one id (`escrowYaGuardado` is check-then-act).

**Impact**

- **Organizer:** on-chain escrow with no **Approve and pay** / **View payment** in Hyto.
- **Volunteer:** paid on-chain or not, the app does not show it. This is why the repo still has no real payment hash.

HMAC binding of the signed XDR is in place and is not this bug. `HYTO_TOKEN_SECRET` shorter than 32 characters, or missing in production, correctly returns 503.

**Suggested fix**

At prepare time, persist predicted `contractId` and the prepare hash on the task row. On `INDEXER_LAGGING`, confirm with RPC `getTransaction` and then save the contract or `hash_pago`. One in-flight deploy per task (unique pending row). Do not add a second in-memory map.

### F3 — P1 — Google return can drop the Gmail session in the UI

**Where:** `components/admin/Entrar.tsx` `iniciarGoogle`. Email OTP uses `entrarConCodigo` and does not have this race.

**How to reproduce**

1. Choose Google. Cavos redirects back with `cavos_auth_code`.
2. The effect stores the code, then `iniciarGoogle` **awaits** `crearAuth()` and only then reads `window.location.search`.
3. If the query string is gone before `handleCallback` (navigation, a second effect, a cleaned URL), the one-time code is spent or missing and sign-in fails.
4. If the header unmounts, `vivo` becomes false and the `.then` returns without `guardarDireccionAdmin`, even when `entrarConGoogle` already set the cookie. The screen can still ask for sign-in.

Open PR #18 describes this and has not landed on `53ec93c`. Rebase it onto current `Entrar.tsx` instead of rewriting it.

**Impact:** new Gmail volunteers fail or look signed out. Organizers who use Google hit the same function. Email-code login does not.

**Suggested fix:** capture `window.location.search` and the redirect URI before any `await`. Apply the session result even if this effect cleaned up. Surface `fijarWallet` errors instead of painting **Signed in** from a local address (`lib/auth/cliente.ts` returns the address when the save fails; `Entrar.tsx` still stores it).

### F4 — P1 — The payout address is not proven

**Where:** `POST /api/sesion/wallet` in `lib/api/sesion.ts`. Optional body `token` is decoded by `walletDelToken` **without** `verificarJwt` (`lib/sesion/correo.ts`). The comment in `fijarWalletHttp` already says the client address does not prove key control. `lib/auth/cliente.ts` posts `{ wallet }` only.

**How to reproduce**

1. Sign in. The Cavos login JWT usually has no `G…`, so the new session stores `wallet: ""`.
2. Before the real device calls `fijarWallet`, `POST /api/sesion/wallet` with any `G…` that passes the format check.
3. That address is locked for this session and becomes `wallet_cobro` on the next evidence upload.
4. A forged JWT in the optional `token` field does not add proof: a matching payload is accepted, and omitting `token` is also accepted.

**Impact:** a stolen `hyto_sesion` cookie, before the volunteer connects, can point payouts at another account. The XDR signer must still match `sesiones.wallet`, so this does not let an attacker release the organizer's USDC. It does choose **who receives** it. Organizer dispute checks that also trust `sesiones.wallet` inherit the same unverified address.

**Suggested fix:** server nonce, Cavos `signMessage` or a SEP-10 challenge, verify, then `guardarWallet`. Ignore unverified JWT payloads.

### F5 — P1 — `wallet_cobro` is not locked to the escrow

**Where:** `lib/api/evidencias.ts` updates `walletCobro` whenever the session wallet differs, with no `contratoEscrow` check. `POST /api/revision/:id/pedir` only sets `estado: "pendiente"` (`lib/api/pedir.ts`).

**How to reproduce**

1. Volunteer uploads. Session wallet is stored on the task.
2. Organizer deploys. The on-chain receiver is that address.
3. Organizer asks for another photo, or the volunteer signs in again (new session, new `G…` if the previous session had not locked one) and uploads.
4. The database address changes. The contract receiver does not.

**Impact:** organizer UI and the #100 preflight can describe a different account than the one that will be paid. Volunteers see the new address on **Account**.

**Suggested fix:** if `contrato_escrow` is set, reject a different `wallet_cobro`. Do not reassign the member after deploy (`lib/api/asignar.ts` still allows it).

### F6 — P1 — Production does not require JWT audience or issuer

**Where:** `lib/sesion/jwt.ts`. Empty issuer list means every `iss` is allowed. Empty audience skips `aud`. Production only blocks the unsigned bypass.

**How to reproduce:** production with a valid Cavos signature key and empty `CAVOS_JWT_AUDIENCE` (the known unset case) accepts a token minted for another audience. Empty `CAVOS_JWT_ISSUER` accepts any issuer on those keys. A Gmail token whose `iss` is not in the list fails closed only when the list is non-empty — so a list that contains only the email issuer locks Google out.

**Impact:** both roles. New Gmail users are the ones who depend on the Google issuer being configured.

**Suggested fix:** in production, refuse to verify when either variable is empty. Set both in Vercel to the real Cavos and Google issuer values and Hyto's audience. Add a unit test that production plus empty audience rejects.

### F7 — P1 — Failed upload looks sent

**Where:** `lib/integrante/rutas.ts` `subirEvidencia`. Any error other than 401/403 returns `evidenciaEjemplo` with `ejemplo: true`. `components/integrante/SubirEvidencia.tsx` then sets phase `lista` ("Evidence sent"). The footnote is "Sample task, until your own tasks load." The JSON `aviso` on a **201** (no payout wallet) is never read.

**How to reproduce**

1. Assigned Gmail volunteer, flaky network or a 500/503 from `/api/evidencias` (for example migration `0005_evidencia_antifraude.sql` not applied — that path returns 503).
2. The screen says **Evidence sent**.
3. Separately: upload with an empty session wallet. The API returns 201 plus `AVISO_SIN_CUENTA` ("This sign-in has no payout account…"). The volunteer still sees success. The organizer later cannot lock the budget ("The task has no payout wallet").

**Impact:** volunteers think the organizer has the photo. Organizers see an empty inbox. Demo mode is worse because the sample object is the fallback.

**Suggested fix:** throw on non-OK responses. Show `aviso`. Do not mark the task in review in local storage unless the POST succeeded.

### F8 — P1 — Demo inbox counts and English copy

**Where:** `lib/ui/etiquetas.ts`, `lib/admin/vista.ts` `enBandeja`, `lib/api/pedir.ts`, `components/admin/Numeros.tsx`, `components/admin/Bandeja.tsx`, `components/admin/ListaEventos.tsx`.

**How to reproduce**

1. Open the inbox. Filter pills use `etiquetaVeredicto`: **Completado**, **Parcialmente completado**, **Insuficiente**.
2. The ZEEK example has four tasks. `enBandeja` keeps a task when it is `en revisión` **or** when a verdict exists and the task is not paid. The welcome-table row has no verdict, so the subtitle says three submissions. Tests lock this in (`lib/admin/vista.test.ts`). The event card's "N pending" uses the same inbox rule (`lib/api/proyectos.ts` `contarBandeja`). The KPI labeled **Pending** is `presupuesto - pagado` in dollars (`Numeros.tsx`), $75 on the example. Volunteer **Mis tareas** counts `estado === "pendiente"` only. Three different "pending" numbers on one demo.
3. On a live review, **Ask for another photo** sets `pendiente` and leaves the verdict row. `enBandeja` still includes it, with the old pill. The local sample path clears the verdict (`aplicarDecision`); the server path does not.

**Impact:** organizer demo. Volunteers see **Pending** / **In review** in English (`etiquetaEstado`) and are not the ones reading the Spanish pills.

**Suggested fix:** English labels for the three verdicts. Rename the dollar KPI (remaining budget). After asking for another photo, clear or ignore the verdict until a new file exists. One definition of "pending" on the event card and the inbox. Coordinate with #89 so this is not implemented twice.

### F9 — P1 — Empty-looking photo

**Where:** `lib/api/evidencias.ts` `MARCADOR_EJEMPLO`; `components/admin/Revision.tsx` photo branch.

**How to reproduce**

1. Open a seeded review. The photo URL is `/api/evidencias/…/foto`. Example blobs return a 64×48 beige SVG (`image/svg+xml`) with no `nosniff`. In the review frame that reads as an empty photo.
2. If `foto` is null and `tarea.frase` is set, the real and sample screens both render **Sample evidence** plus the title. The true empty state ("No photo yet") only runs when there is no phrase either. `real` is not consulted in that branch.

**Impact:** the pitch review does not show work. A live task whose photo URL failed but whose AI phrase was saved is labeled as a sample.

**Suggested fix:** serve a real PNG placeholder for example blobs. Show **Sample evidence** only when the review is not live. Keep **No photo yet** whenever the URL is missing on a live task.

### F10 — P1 — Camera checks do not bind the device, and replay is per instance

**Where:** `components/integrante/SubirEvidencia.tsx` (camera via `getUserMedia`, canvas JPEG). `lib/api/evidencias.ts` (work tasks: JPEG + token + freshness). `lib/evidencia/token.ts` (`usados` map). `lib/evidencia/frescura.ts` (3-minute window; client timestamp accepted when EXIF is absent).

**How to reproduce**

1. In the browser, work tasks do open the camera and reject the file picker. That part is real.
2. `POST /api/evidencias/token`, then `POST /api/evidencias` with any JPEG and `capturadaEn` set to now. No camera attestation is required. A photo with no EXIF passes on the client clock.
3. Spend the same `jti` on two serverless instances within two minutes. The in-memory set does not see the other instance, so the second upload can pass.

Receipts (reembolso) correctly allow a chosen PDF/JPEG/PNG/WebP. That is not this finding.

**Impact:** a volunteer who can call the API can submit a gallery JPEG as "camera" proof. Organizers still see the AI note and must approve; the AI does not pay. Duplicate bytes are rejected by `sha256` when the second request hits a store that already has the hash.

**Suggested fix:** persist spent `jti` in Postgres with a TTL. State in the UI that the server cannot prove the JPEG came from `getUserMedia`. Do not pretend the HMAC token is a camera attestation.

### F12 — P2 — Demo limits and smaller UX traps

**By design (not bugs):** with `HYTO_DEMO_LOGIN=1`, demo sessions have an empty wallet. `POST /api/firma` and `POST /api/firma/enviar` return 403. Creating an event returns 403. **Get ready to be paid** is hidden and `/api/usdc` returns 403. **Approve** on a sample review does not move USDC (`lib/admin/remoto.ts` local buttons). Leaving demo deletes the session cookie.

**Still sharp on a live demo**

- Join (`POST /api/join`) adds membership and does not assign tasks. **Mis tareas** stays empty until the organizer assigns. A new Gmail volunteer can believe the code failed.
- `fondeado === null` (indexer lag) shows neither **Fund** nor **Approve and pay** (`lib/admin/remoto.ts`). After a successful fund the button can vanish until the indexer catches up.
- `lib/auth/cliente.ts` still says the Hyto cookie lasts 14 days. The cookie cap is 24 hours.
- Organizer USDC preflight does not check XLM. A wallet with USDC and no XLM fails later at sign time. The fee-bump message mentions Friendbot; the volunteer button does not.

**Suggested fix:** post-join empty state that says the organizer still has to assign a task. Treat unknown escrow balance as "checking" with retry, and keep **Fund** available when a contract exists and balance is not a confirmed positive. Fix the 14-day comment when touching auth.

## 5. Volunteer path a follow-up should walk

1. Google sign-in (F3) creates a `voluntario` and a `G…` that is not yet on testnet (F1, F4).
2. Join code adds the person to the event and assigns nothing (F12).
3. **Account** shows the address and **Get ready to be paid**, which 400s until someone runs Friendbot by hand (F1).
4. **Mis tareas** → camera upload. A network error still says **Evidence sent** (F7). A missing wallet still returns 201 (F7).
5. Organizer inbox may show a Spanish pill and a blank SVG (F8, F9). **Lock budget** waits on the trustline (F1) and can lose the contract id (F2).
6. **Approve and pay** needs a funded escrow and writes `hash_pago` only when the release re-read says the milestone is released (holds). No such hash is stored in this repository today.
