# Hyto code audit — 2026-09-30

- **Repo:** [Hyto-App/hyto](https://github.com/Hyto-App/hyto), branch `main` at `db82b93` (2026-09-30).
- **Scope:** API routes (`app/api`), auth and session (`lib/sesion`, `lib/auth`, `lib/api/sesion.ts`), the escrow and Trustless Work flow (`lib/escrow`, `lib/api/firma.ts`), the Cavos integration, USDC trustline, DB schema and migrations (`lib/db`, `drizzle/`), env var handling, errors, tests, i18n, AI review (`lib/revision`).
- **Method:** read-only clone plus `npm ci`, `npm test`, `npx tsc --noEmit`, `npm audit --omit=dev`. Stellar Raven MCP (docs, skills, ecosystem data). Read-only Horizon testnet queries. No transactions were signed or submitted, and no funds moved.
- **Rule:** every claim cites a file and line in `main` or an external source. Where something is an inference and not a fact, it says so.

---

## 1. Executive summary

Hyto's server-side guards on the escrow flow are solid. The organizer check is per project (`lib/api/organizador.ts`). The signer is read from the signed XDR, not from the request body (`lib/escrow/xdr.ts`, `lib/api/firma.ts:80-85`). A task is only marked paid after `release_funds` is confirmed and the escrow is re-read (`lib/api/firma.ts:235-260`). JWT verification is strict RS256 with `exp`/`nbf` checks (`lib/sesion/jwt.ts`). `tsc` passes with no errors and 286 of 287 unit tests pass.

The product still hasn't moved a USDC payment. Read in code, the main blockers and risks are:

1. **No USDC payment can go through until the volunteer's payout wallet has a USDC trustline, and nothing checks for it before deploy.** Trustless Work v2 rejects a multi-release deploy with `422 ESCROW_RECEIVER_TRUSTLINE_MISSING` when any `milestones[].receiver` lacks the trustline (Trustless Work skill, `api/v2/multi-release.md` and `core-concepts.md`, "Receiver trustline preflight"). Hyto's deploy (`lib/api/firma.ts:144-194`) doesn't check this, and the only trustline UI is the self-paid "Prepare USDC" flow, which is the one failing today.
2. **"Prepare USDC" builds a self-paid classic `changeTrust` tx on the server and asks Cavos to `signXdr` it** (`lib/api/usdc.ts:68-80`, `lib/integrante/prepararUsdc.ts:23-40`). That needs an account that already exists and holds XLM. `@cavos/kit` 0.2.5 ships a sponsored `addTrustline()` (relayer pays the reserve) that the repo already uses elsewhere (`lib/integrante/usdc.ts:56`), but not on this path. The signing path also never checks `wallet.status` (`lib/escrow/firmarCliente.ts:149-157`), and a `needs-device-approval` wallet can't sign.
3. **The session wallet isn't proven.** `POST /api/sesion/wallet` stores any `G…` the client sends when the JWT doesn't carry one (`lib/api/sesion.ts:97-112`, the code says so itself). The payout wallet `wallet_cobro` also comes straight from a form field (`lib/api/evidencias.ts:98,126`), with no signature and no trustline check, and it can change after the escrow is deployed.
4. **Stored-XSS risk through evidence photos.** Any `image/*` type is accepted, including `image/svg+xml` (`lib/api/evidencias.ts:195-198`), and it's served back from Hyto's own origin with the client-supplied content type (`lib/api/evidencias.ts:69-71`). There are no `X-Content-Type-Options`/CSP headers (`next.config.ts`).
5. **`CAVOS_JWT_AUDIENCE` and `CAVOS_JWT_ISSUER` are optional.** When they're empty, `aud`/`iss` aren't checked (`lib/sesion/jwt.ts:63-64,95-99`). With a shared JWKS, a token minted for another Cavos app could open a Hyto session. That part is an inference that depends on Cavos key sharing, which the Cavos docs don't document.
6. **Serverless correctness:** the rate limiter (`lib/escrow/limite.ts`) and the prepared-contract cache (`lib/api/firma.ts:19`) are per-process `Map`s. On Vercel they don't hold across instances.
7. **Upload limit mismatch:** the code allows 8 MB (`lib/api/evidencias.ts:10`), but Vercel Functions reject request bodies over 4.5 MB with `413 FUNCTION_PAYLOAD_TOO_LARGE` ([Vercel docs](https://vercel.com/docs/functions/limitations)).
8. **No CI.** The repo has no `.github/` directory, and in a clean checkout `npm test` fails 1 test (see §3.6).

Top P0s: sponsored trustline via Cavos `addTrustline` plus a receiver-trustline preflight before deploy; proof of wallet ownership (signed challenge) and locking `wallet_cobro` once deployed; blocking SVG and adding security headers; requiring `CAVOS_JWT_AUDIENCE`/`CAVOS_JWT_ISSUER` in production; saving the predicted `contractId` in the DB at prepare time; adding CI.

## 2. What works well (backed by code)

- **Signer comes from the XDR, not the body.** `leerInvocacion` reads the invoked contract, the function, and the Soroban auth entries, and `enviarFirmaHttp` requires exactly one signer equal to `sesiones.wallet` (`lib/escrow/xdr.ts:60-109`, `lib/api/firma.ts:80-85`).
- **Per-project organizer authorization** for deploy, fund, approve and release (`lib/api/organizador.ts:22-46`, `lib/api/firma.ts:37,46,104-109`).
- **"Paid" requires on-chain evidence:** `release_funds` on this task's contract, the v2 submit confirmed, a 64-hex hash, and a re-read escrow showing milestone 0 released (`lib/api/firma.ts:235-260`).
- **Dispute resolution:** the resolver is checked against the escrow's `disputeResolvers` both at prepare and at submit (`lib/escrow/resolver.ts`, `lib/api/firma.ts:87-101`), and amounts are compared in 7-decimal integer units (`lib/escrow/resolver.ts:unidadesDe`).
- **USDC trustline XDR is validated server-side:** testnet passphrase, a single `changeTrust` op for the exact code and issuer, source equal to the session wallet, and an ed25519 signature check (`lib/integrante/trustline.ts:27-56`).
- **Correct USDC identity.** The issuer `GBBD47IF…LFLA5` (`lib/integrante/identidades.ts:7`) and the derived SAC `CBIELTK6YBZJU5UP2WWQEUCYKLPU6AUNZ2BQ4WWFEIE3USCIHMXQDAMA` (`lib/escrow/desplegar.ts:8`) both match the Trustless Work v2 docs ("Form A" trustline example) and Horizon (see §6).
- **JWT verification:** RS256 only, `crit` rejected, `kid`/issuer-scoped key selection, JWKS cached only when non-empty, HTTPS-only JWKS URLs, and the unsigned bypass refused in production (`lib/sesion/jwt.ts`).
- **Session cookie** is `HttpOnly; SameSite=Lax; Secure` in production, capped at 24 h (`lib/sesion/cookie.ts:18-21`).
- **Only one `NEXT_PUBLIC_` variable** exists (`NEXT_PUBLIC_CAVOS_APP_ID`, `lib/config/publico.ts`). No server secret is read in client code.
- **Private Vercel Blob storage** (`access: "private"`, `lib/blob/fotos.ts:41-46`). Photos are served through an authorized route.
- **Fee-bump is rejected up front** with a helpful message (`lib/api/firma.ts:71-79`), matching the Trustless Work v2 `STELLAR_TX_FEE_BUMP_REJECTED` code handling (`lib/escrow/modulo.ts:148-153`).
